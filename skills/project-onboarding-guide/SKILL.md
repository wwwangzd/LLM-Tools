# Project Onboarding Guide

## 概述

基于仓库中的真实证据，快速生成一份便于上手的项目梳理说明。用户未指定路径时，默认将当前工作目录视为目标项目；如果用户还补充了额外说明，需要将这些要求合并进同一次分析，而不是忽略它们。

## 核心流程

1. 明确范围。
- 除非用户明确指定其他路径，否则默认将当前工作目录作为目标项目。
- 先识别用户的附加要求，例如语言、受众、关注重点、输出格式、深度或排除项。
- 除非用户明确要求省略，否则保留项目上手梳理的三个核心目标：
  项目概览、关键目录说明、启动或运行流程。

2. 先做一次快速盘点。
- 在手动读文件前，先运行 `python3 scripts/project_snapshot.py <目标路径>`。
- 利用扫描结果识别可能的技术栈、根目录清单文件、候选命令和高价值目录。
- 只读取真正有帮助的文件；优先使用 `rg --files` 配合定向阅读，而不是把整个仓库都扫一遍。

3. 收集可信证据。
- 优先按以下顺序检查：`README*`、根目录清单文件、workspace 或子应用清单、任务执行文件、容器相关文件、最后才是入口源码文件。
- 尽量采用 `package.json`、`Makefile`、`pyproject.toml`、`Cargo.toml`、`go.mod`、`docker-compose.yml`、`compose.yaml`、`Taskfile.yml`、`justfile` 等文件中明确声明的命令。
- 任何仅凭源码结构推测出来的结论，都要明确标注为“推断”。

4. 梳理项目结构。
- 只解释那些真正有助于新协作者上手的目录和文件。
- 重点关注根目录以及主要可运行的应用或服务。
- 对于生成产物目录或纯辅助目录，如果不是理解项目核心所必需，应单独归类或弱化描述。
- 判断目录职责时要看里面的内容，而不是只看目录名。

5. 说明运行流程。
- 如果仓库中提供了对应信息，要区分环境准备、开发启动、生产构建或启动、测试命令。
- 如果项目包含多个服务或应用，先说明默认或主要路径，再补充其他可选路径。
- 明确指出哪些命令是仓库中显式声明的，哪些是根据结构推断出来的。

6. 组织输出结果。
- 默认使用简洁结构：
  `项目概览`
  `关键目录`
  `运行流程`
  `补充说明`
- 必要时引用最关键的支撑文件。
- 如果存在不确定、文档缺失或证据冲突的情况，要直接说明，不要默默猜测。
- 除非用户明确要求使用其他语言，否则最终生成的项目梳理文档一律使用简体中文表述。

## 处理额外说明

- 将用户附加的要求合并进同一份输出中。
- 当用户指定了关注重点，例如前端、后端、部署、测试或某个特定包时，要相应调整回答重点。
- 除非用户明确要求缩小范围，否则保留默认的项目上手梳理结构。

## 大型仓库处理

- 先识别 monorepo 信号，例如 `apps/`、`packages/`、`services/`、workspace 清单、`turbo.json`、`nx.json`，或多个一级包清单文件。
- 先从根目录建立整体认识，再只深入检查最符合用户目标的主包或主应用。
- 优先先广后深，最后再钻取最关键的模块。

## 约束原则

- 不要把所有目录都一股脑列出来，只突出新协作者真正需要先理解的几个目录。
- 不要把 `dist/`、`build/`、`coverage/`、`node_modules/` 这类生成目录误当成核心架构，除非它们确实与用户问题直接相关。
- 当仓库没有明确记录运行方式时，不要虚构命令；可以给出最合理的推断，但必须说明缺失了哪些证据。

## 资源

- 用 `scripts/project_snapshot.py` 做第一轮项目盘点。
- 当仓库较大、运行路径不明确，或不同文件之间存在证据冲突时，读取 `references/inspection-guide.md`。
