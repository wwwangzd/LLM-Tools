# 日常测试驱动开发

## 核心原则

先用测试定义期望行为并确认它会失败，再编写让它通过的最少代码。

测试应证明可观察行为，而不是复述实现细节。

## 红—绿—重构

### 1. 红：定义行为并确认失败

1. 明确本次只改变哪一项可观察行为。
2. 找到项目现有测试框架和最接近的测试示例。
3. 编写一个名称清晰、只验证一种行为的最小测试。
4. 运行该测试并确认：
   - 测试确实失败，而不是测试代码运行出错。
   - 失败信息符合预期。
   - 失败原因是行为尚未实现或 Bug 仍能复现。

测试第一次就通过时，不要进入实现阶段。先判断：

- 该行为是否已经存在；
- 测试是否断言了错误对象或错误层级；
- 测试是否遗漏了真正的失败条件。

### 2. 绿：编写最少实现

只编写足以让当前失败测试通过的代码：

- 不提前加入未被需求或测试要求的配置和扩展点。
- 不混入无关重构、格式化或顺手优化。
- 测试失败时优先修改实现；只有需求或断言本身错误时才修改测试。

运行当前测试，确认它通过；随后运行直接相关的测试，发现回归立即处理。

### 3. 重构：保持绿色

仅在测试通过后整理代码：

- 消除本次产生的重复。
- 改善命名和局部结构。
- 移除本次产生的死代码。

每次小步重构后重新运行相关测试，不在重构阶段增加新行为。

## 不同任务的处理

### Bug 修复

先编写能够稳定复现原始问题的回归测试，确认它因该 Bug 失败，再修复根因。这个测试既证明修复有效，也防止问题再次出现。

根因尚未明确时，先使用 `systematic-debugging`，不要用测试驱动流程替代根因调查。

### 新功能或行为变更

从使用者视角定义输入、输出、错误和边界情况。每次只推进一个行为的红—绿循环。

### 不改变行为的重构

不必人为制造失败测试。先确认覆盖相关行为的现有测试通过，再小步重构并持续保持绿色。如果缺少必要覆盖，先补充描述现有行为的特征测试。

### 已经存在实现代码

不要删除或覆盖用户已有工作。先补充能够证明目标行为的测试，并如实说明没有完整经历测试优先过程；随后用测试约束后续修改。

## 可以不执行完整 TDD 的情况

以下任务可以采用替代验证：

- 纯文档修改。
- 纯配置修改。
- 自动生成且不应手工维护的代码。
- 明确的一次性探索或抛弃式原型。
- 当前项目没有可执行测试入口，且新增测试基础设施明显超出任务范围。

跳过时必须说明原因，并选择与风险相称的替代验证。用户明确要求测试优先时，不自行跳过。

## 测试质量

确保测试：

- 验证行为和结果，而不是私有实现步骤。
- 一个测试聚焦一种行为。
- 名称描述输入条件和预期结果。
- 优先使用真实代码，只在隔离慢速、外部或不稳定依赖时使用 Mock。
- 不为测试向生产接口添加无业务意义的方法。
- 覆盖与本次需求相关的成功、边界和错误路径。

添加或修改 Mock、测试工具或测试专用清理逻辑时，完整阅读
[`references/testing-anti-patterns.md`](references/testing-anti-patterns.md)。

## 过程记录

在交付时保留足够证据说明：

```text
RED：运行了什么测试，因什么预期原因失败
GREEN：实现后同一测试如何通过
RELATED：哪些相关测试通过
EXCEPTIONS：跳过了什么，以及采用了什么替代验证
```

完成实现后，使用 `verification-before-completion` 执行最终验收。
