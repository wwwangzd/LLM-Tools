# 测试反模式

添加或修改 Mock、测试工具，或者准备向生产代码加入测试专用接口时，使用本参考。

## 1. 测试 Mock，而不是真实行为

反模式：

```typescript
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

这只能证明 Mock 被渲染，不能证明页面提供了正确行为。

优先：

```typescript
expect(screen.getByRole('navigation')).toBeInTheDocument();
```

如果必须 Mock 子组件，也应断言被测组件在该依赖存在时的行为，不要断言 Mock 本身。

## 2. 为测试污染生产接口

不要只为了 `afterEach` 或测试清理，向生产类添加没有业务含义的 `destroy()`、`reset()` 或数据暴露方法。

先判断资源生命周期由谁负责：

- 生产对象确实拥有该资源时，可以提供正式生命周期接口。
- 只有测试需要时，把清理逻辑放入测试工具或测试夹具。

不要为了便于断言而扩大生产 API。

## 3. 不理解依赖就 Mock

Mock 前先回答：

1. 真实依赖有哪些副作用？
2. 被测行为是否依赖其中任何副作用？
3. 能否只隔离真正慢速、外部或不稳定的最低层操作？

高层方法既包含外部调用又负责写入配置时，不要整个 Mock 掉高层方法；否则测试可能绕过它真正要验证的行为。

不确定时，先使用真实实现运行测试并观察必要行为，再在正确边界加入最少 Mock。

## 4. Mock 数据结构不完整

Mock 响应应符合真实接口的类型和结构，不能只保留当前断言碰巧使用的字段。

优先使用：

- 类型检查或 schema 校验。
- 官方示例或真实响应夹具。
- 集中维护的测试构造器。

缺失字段会让单元测试通过、集成环境失败。

## 5. Mock 复杂度超过测试价值

出现以下情况时重新考虑测试层级：

- Mock 设置比测试逻辑更长。
- 为让测试通过需要 Mock 大部分依赖。
- 删除一个 Mock 后测试含义完全改变。
- 无法解释每个 Mock 为什么必要。

此时真实组件参与的集成测试通常更简单、更可信。

## 检查清单

在提交测试前确认：

- 断言描述真实可观察行为。
- 每个 Mock 都有明确的隔离目的。
- 必要副作用没有被意外抹掉。
- Mock 数据符合真实结构。
- 生产代码没有被测试专用接口污染。
- 测试失败时能够给出有意义的行为差异。
