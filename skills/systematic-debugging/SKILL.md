# 日常系统化调试

## 核心原则

先建立事实，再提出修复。优先修复根因，不用猜测性改动掩盖症状。

- 区分事实、假设和结论。
- 一次验证一个假设，保持改动最小。
- 用户只要求诊断时，报告根因和修复方向，不擅自修改代码。
- 用户要求修复时，先完成根因调查，再进入测试驱动实现。

## 调试流程

### 1. 建立事实

1. 完整阅读错误、警告和调用栈，记录路径、行号、错误码及失败命令。
2. 用最小步骤稳定复现，确认预期行为与实际行为。
3. 检查近期代码、依赖、配置和环境变化。
4. 如果无法复现，明确说明缺失证据，继续采集日志、输入和运行环境；不要猜测根因。

### 2. 定位故障边界

从错误出现的位置向上追踪数据和控制流：

- 谁调用了失败代码？
- 关键参数在哪里产生和改变？
- 哪个边界第一次出现错误状态？
- 同一代码库中是否存在可工作的相似实现？

多组件系统应在组件边界记录输入、输出、配置传播和状态，先确定故障发生在哪一层，再深入该层。

错误位于深层调用链、参数来源不清或测试产生环境污染时，完整阅读
[`references/root-cause-tracing.md`](references/root-cause-tracing.md)。

### 3. 验证单一假设

用一句话写明：

```text
我认为 <X> 是根因，因为 <Y 证据>。
```

然后：

1. 设计能区分该假设与其他解释的最小实验。
2. 一次只改变一个变量。
3. 运行实验并记录结果。
4. 假设不成立时撤回该方向，更新证据并形成新假设，不叠加猜测性修复。

连续多个独立假设均失败时，重新检查复现条件、环境差异、隐藏状态和架构假设；如果修复开始要求大范围重构，先与用户讨论设计问题。

### 4. 解决根因

如果任务只要求诊断，输出根因、证据、影响范围和最小修复建议。

如果任务要求修复：

1. 使用 `test-driven-development`，先创建能够复现问题的失败测试或最小可执行复现。
2. 实施只针对已确认根因的最小修改。
3. 不混入无关重构或顺手优化。
4. 对可能绕过入口校验的高风险数据流，在必要层级增加与风险相称的校验；不要机械地给所有层增加重复检查。
5. 移除本次添加且不再需要的临时诊断代码。

### 5. 验证与交付

使用 `verification-before-completion` 在最后一次相关修改之后验证：

- 原始问题不再复现。
- 回归测试通过。
- 相关测试、类型检查、Lint 或构建未被破坏。
- 未验证项和残余风险已明确报告。

## 生产事故中的止损

在生产影响持续扩大时，可以先执行用户授权范围内的回滚、关闭功能、隔离流量或其他可逆止损措施。

必须：

- 明确标注这是临时止损，不是根因修复。
- 记录触发条件、操作和结果。
- 服务恢复后继续根因调查。
- 未验证根因前，不把重试、延长超时或吞掉错误描述为最终修复。

## 异步和偶发失败

测试依赖 `sleep`、固定延迟、并发时序或在 CI 中偶发失败时，完整阅读
[`references/condition-based-waiting.md`](references/condition-based-waiting.md)，优先等待真实条件而不是猜测耗时。

## 输出格式

按任务实际情况报告：

```text
现象与复现：
关键证据：
已确认根因：
排除的假设：
修复或建议：
验证结果：
未确定项与风险：
```
