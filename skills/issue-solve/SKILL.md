# 问题清单处理

按“补齐输入 → 获取问题 → 评估分流 → 修改验证 → 统一结论”的顺序执行。保持修改低侵入，只处理用户指定模块和问题来源覆盖的范围。

## 1. 补齐必需输入

开始获取问题或修改代码前，确认以下两项：

- **问题来源**：用户粘贴的问题、问题清单链接、表格、文档、截图或本地文件。
- **涉及模块**：产品模块、页面、功能目录或仓库范围。

任一项缺失时，显式向用户获取；两项都缺失时在同一次交互中一起询问。不得自行猜测来源或模块。

若来源需要权限、连接器或内部服务：

1. 先按工作区规则检查并使用公司内部服务工具；飞书/Lark 等内部来源优先使用 bytedcli MCP。
2. 尽量读取表格字段、状态、描述、截图和附件；能够看到附件图片时一并核对。
3. 无法访问时说明具体限制，请用户粘贴内容、导出文件或补充权限，不得臆造问题。

## 2. 获取并整理候选问题

仅保留与指定模块有关且仍待处理的记录。结合状态字段、验收备注、最近更新和代码现状去重；状态语义不明确时先向用户确认。

先输出或形成内部编号清单，每项至少记录：

- 来源中的编号或可追溯标识；
- 问题描述与期望效果；
- 截图/附件是否可见；
- 涉及模块、功能、页面、组件或交互；
- 当前状态及判断依据。

不要仅凭列表文字直接修改。先在当前代码和运行行为中确认问题仍存在，并通过复现、证据收集和数据流追踪定位根因。修改既有行为时先补充能够暴露原问题的测试，再实施最小修复。

## 3. 成本与决策分流

在编码前逐项分类：

### 可直接处理

问题边界和验收标准明确，改动局限在当前模块，依赖可用，预计能以小范围修改及相称验证完成。直接实施。

### 成本过高，暂不处理

出现以下任一情况时先保留，不进入实现：

- 需要跨多个仓库或改动公共契约、架构、数据模型；
- 需要大面积重写、迁移或引入新基础设施；
- 所需依赖、权限、设计资产或环境缺失，无法可靠完成；
- 工作量明显超出当前问题批次或单个可审查变更；
- 风险与收益不匹配，低侵入方案不能满足需求。

记录具体成本来源和建议后续路径，不用模糊的“太复杂”代替分析。

### 需要用户决策

以下情况暂停该问题并向用户交互，获得选择后再继续：

- 存在两个以上会产生不同产品体验或技术边界的合理方案；
- 问题描述、设计稿与现有行为冲突；
- 是否抽取公共能力、改变交互语义或扩大范围会显著影响结果；
- 缺少关键验收标准，合理假设可能偏离用户意图。

将同一批次的决策问题尽量合并询问。给出推荐项、各方案影响和必要证据；等待用户选择时，可继续处理其他不依赖该决策的问题。

## 4. 针对每个问题执行三项检查

每次具体修改都检查以下方面，并只清理与当前模块、当前问题有明确关系的内容。

### 4.1 优先使用通用能力

搜索现有公共函数、服务、组件库、设计 token、通用交互组件及同类实现。已有能力满足需求时直接复用，避免重复实现相同逻辑；问题涉及界面时，优先使用项目指定组件库及已有按钮、提示、加载态、弹窗、空态等通用能力。

不要为迁就局部实现而复制通用组件；也不要为了形式统一强行替换行为不同的组件。

### 4.2 对齐相似设计与实现

检查同一产品中是否已有相同或高度相似的业务逻辑、状态处理、界面、设计、交互或响应式规则：

1. 能直接复用且语义一致时复用。
2. 多处存在稳定、真实的重复需求，抽取后能降低重复且不会引入复杂 API 时，才考虑提取通用能力。
3. 没有必要提取时，不新增抽象；实现方式与既有同类能力对齐。问题涉及界面时，还要对齐视觉、状态文案、操作反馈、键盘/无障碍和响应式行为。

抽取公共能力属于需要显著扩大改动范围时，归入“需要用户决策”或“成本过高”。

### 4.3 清理无用、冗余和过时内容

审计触达模块中的：

- 未引用或被新实现取代的代码与样式；
- 重复声明、局部重复动画、已由通用组件覆盖的覆盖样式；
- 过时的逻辑分支、设计、状态、内容、样式、文案和注释；
- 修改后产生的未使用导入、死代码和测试残留。

删除前必须用引用搜索、动态类名检查、条件分支和运行行为证明其无用。不要删除由模板字符串、状态映射、运行时选择器或平台差异动态使用的内容；不要顺手清理无关存量问题。

## 5. 实施与验证

- 改动前检查目标仓库状态，保留用户已有修改。
- 先修根因，再做最小范围实现；不主动扩大功能。
- 为修复补充能覆盖原始问题的测试，先确认测试能因原问题失败，再使其通过。
- 按风险运行定向测试、模块测试、类型检查、格式/差异检查及受影响平台构建。
- 问题涉及界面且具备可运行环境时执行视觉或交互核对；无法视觉验证时明确标注。
- 完成前获取最后一次修改之后的验证证据，不能依赖修改前或较早的结果。
- 除非用户明确要求，不提交、不推送、不发起 MR，也不更新外部问题状态。

## 6. 输出统一结论

最终回复必须包含以下两部分，并保留来源编号：

### 已修复

按序号列出：

1. 问题与原始编号；
2. 根因；
3. 实际修改；
4. 通用能力复用、设计对齐或清理结果；
5. 验证证据。

### 未修复

按序号列出：

1. 问题与原始编号；
2. 分类：成本过高、待用户决策、来源不足、无法复现、依赖缺失或其他；
3. 未处理的具体原因；
4. 推荐的下一步或所需决策。

没有未修复问题时明确写“无”。另外简述验证未覆盖项和残余风险，不把未验证内容表述为已完成。
