# 日常测试驱动开发

## 核心原则

用测试约束本次修改，而不是在实现完成后才用测试确认结果。

- 新功能、Bug 修复和其他可观察行为变更：先获得正确的失败测试，再修改生产代码。
- 不改变行为的纯重构：先确认相关测试通过，再小步修改并持续保持绿色。

## 修改前门禁

在编辑生产代码之前：

1. 阅读需求、相关实现和最接近的测试，明确本次修改的可观察结果。
2. 运行直接相关的现有测试，记录当前基线。
3. 判断本次任务属于哪条路径：
   - **行为变更**：新功能、Bug 修复、边界或错误处理变化，进入红—绿—重构。
   - **纯重构**：外部行为不变，只调整内部结构，进入绿色重构流程。
   - **例外任务**：符合下文例外条件时，说明原因并采用替代验证。
4. 行为变更进入实现前，先确认存在因目标行为而失败的测试；没有则新增或修改测试并运行确认。
5. 基线中与本任务无关的失败应单独处理或明确报告。

## 行为变更：红—绿—重构

### 1. 红：定义行为并确认失败

1. 编写或调整一个名称清晰、只验证一种行为的最小测试。
2. 从使用者视角断言输入、输出、错误或边界行为，不复述私有实现步骤。
3. 运行该测试并确认：
   - 测试失败，而不是测试代码或环境出错。
   - 失败信息符合预期。
   - 失败原因是目标行为尚未实现，或原始 Bug 仍能复现。

测试第一次就通过时，不要进入实现阶段。检查：

- 目标行为是否已经存在；
- 断言是否落在错误对象或错误层级；
- 测试是否遗漏了真正的失败条件；
- 本次需求是否其实不改变行为。

### 2. 绿：编写最少实现

只编写足以让当前失败测试通过的代码：

- 不提前加入未被需求或测试要求的配置和扩展点。
- 不混入无关重构、格式化或顺手优化。
- 测试失败时优先修改实现；只有需求或断言本身错误时才修改测试。

重新运行同一测试，确认它通过；随后运行直接相关的测试，发现回归立即处理。

### 3. 重构：保持绿色

仅在测试通过后整理本次相关代码：

- 消除本次产生的重复。
- 改善命名和局部结构。
- 移除本次产生的死代码。

每次小步重构后重新运行相关测试，不在重构阶段增加新行为。下一个行为使用新的 RED 循环。

## 纯重构：绿色基线流程

纯重构不必人为制造失败测试。

1. 先运行覆盖相关行为的现有测试，确认基线为绿色。
2. 如果关键行为缺少覆盖，先添加描述现有行为的特征测试并确认通过。
3. 每次只做一个小的结构修改。
4. 每个小步后重新运行相关测试。
5. 一旦发现需要改变外部行为，停止重构路径，改走 RED 循环。

## Bug 修复与根因调查

先使用 `systematic-debugging` 确认根因，再用回归测试稳定复现原始问题。不要用一个碰巧失败但与根因无关的测试替代 RED。

修复后，同一回归测试应从预期失败变为通过。

## 已有实现和中途接入

项目原有实现无需删除；TDD 约束的是本次修改顺序。

如果当前任务已经先修改了生产代码：

1. 停止继续扩展实现。
2. 仅在安全且不会影响用户已有改动时，撤回自己本次尚未验证的实现修改，先建立 RED。
3. 如果无法安全区分或撤回修改，保留现场，先补充能够证明目标行为的测试，并如实说明本次没有完整经历测试优先过程。
4. 后续修改继续受测试约束，不用新增测试为既有实现倒推合理性。

## 可以不执行完整 TDD 的情况

以下任务可以采用替代验证：

- 纯文档修改。
- 纯配置修改。
- 自动生成且不应手工维护的代码。
- 明确的一次性探索或抛弃式原型。
- 当前项目没有可执行测试入口，且新增测试基础设施明显超出任务范围。

跳过时必须说明原因，并选择与风险相称的替代验证。用户明确要求测试优先时，不自行跳过。

## 测试质量

确保测试：

- 验证可观察行为和结果，而不是私有实现步骤。
- 一个测试聚焦一种行为。
- 名称描述输入条件和预期结果。
- 优先使用真实代码，只在隔离慢速、外部或不稳定依赖时使用 Mock。
- 不为测试向生产接口添加无业务意义的方法。
- 覆盖与本次需求相关的成功、边界和错误路径。

添加或修改 Mock、测试工具或测试专用清理逻辑时，完整阅读
[`references/testing-anti-patterns.md`](references/testing-anti-patterns.md)。

## 过程记录

在交付时保留足够证据说明：

```text
BASELINE：修改前运行了哪些相关测试，结果如何
RED：哪个测试因什么预期原因失败
GREEN：实现后同一测试如何通过
RELATED：哪些相关测试通过
EXCEPTIONS：跳过了什么，以及采用了什么替代验证
```

纯重构可以将 `RED` 标记为“不适用”，但必须提供修改前后的绿色基线。

完成实现后，使用 `verification-before-completion` 执行最终验收。
