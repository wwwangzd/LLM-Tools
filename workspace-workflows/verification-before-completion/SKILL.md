# 提交或完成前验证

## 核心原则

没有最后一次相关修改之后产生的验证证据，就不要声称工作已经完成或检查已经通过。

验证强度应与改动范围和风险相称；不机械执行无关命令，也不把局部结果推断成整体成功。

## 验收流程

### 1. 明确需要证明的结论

重新阅读用户需求和本次修改，列出需要证明的事项，例如：

- 原始问题不再复现。
- 新行为符合需求。
- 回归测试有效。
- 相关代码可以通过类型检查、Lint 或构建。
- 没有遗漏明确要求。

### 2. 选择验证方式

优先使用项目已有命令和约定。按任务选择：

- 原始复现步骤或回归测试。
- 本次修改对应的定向测试。
- 直接相关的测试集。
- 全量测试。
- 类型检查、Lint、格式检查或构建。
- 必要的运行时、界面或产物检查。
- 对照需求逐项检查。
- 检查版本控制差异，确认实际修改范围。

高风险、跨模块、公共接口或发布相关修改应扩大验证范围。纯文档、局部配置或低风险修改可以使用更小的验证集合，但要说明依据。

### 3. 获取最新证据

在最后一次相关修改之后完整运行所选命令。

不要依赖：

- 修改前或较早的运行结果。
- “应该通过”“看起来没问题”等推断。
- 只运行一部分便声称全部通过。
- 其他 Agent 或工具的成功报告而不独立检查产物。

### 4. 阅读完整结果

对每项验证检查：

- 实际执行的命令或步骤。
- 退出码。
- 通过、失败和跳过数量。
- 错误与警告。
- 结果是否真正支持准备作出的结论。

命令因依赖、权限、环境或外部服务无法运行时，不要声称通过；报告阻塞原因和仍未验证的范围。

### 5. 报告实际状态

只有证据支持时才报告成功。存在失败或缺口时，直接报告当前状态，不使用模糊措辞掩盖。

使用以下结构：

```text
验证结果：
- <命令或步骤>：通过/失败（关键结果）

需求检查：
- <需求>：满足/未满足/未验证

未验证项与残余风险：
- <内容；没有则写“无”>
```

## 特定结论需要的证据

| 准备作出的结论 | 至少需要 |
|---|---|
| Bug 已修复 | 原始症状或回归测试在修复后通过 |
| 回归测试有效 | 测试曾因原始问题正确失败，修复后通过 |
| 测试全部通过 | 完整测试命令显示零失败 |
| 构建成功 | 构建命令退出码为 0 |
| 需求已完成 | 逐项检查明确需求，而不只是测试通过 |
| 委派任务已完成 | 检查实际产物或差异，并运行必要验证 |

如果现有证据只支持较小结论，就只陈述该较小结论。
