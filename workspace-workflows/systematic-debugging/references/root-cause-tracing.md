# 根因反向追踪

当错误出现在深层调用栈、错误参数来源不清，或测试产生了意外文件和状态时，沿调用链向上追踪到最初触发点。

## 追踪步骤

### 1. 准确描述症状

记录实际错误、失败操作、输入、工作目录和环境，不先解释原因。

```text
症状：git init 在源码目录中执行
```

### 2. 找到直接原因

定位直接产生症状的代码和当时收到的值。

```typescript
await execFileAsync('git', ['init'], { cwd: projectDir });
// projectDir === ''
```

### 3. 逐层询问调用来源

持续追问：

- 谁调用了这里？
- 调用者传入了什么？
- 这个值从哪里读取、转换或默认生成？
- 哪一层第一次出现无效值？

示例：

```text
git init 收到空目录
← WorkspaceManager 收到空 projectDir
← Session.create() 传入空字符串
← 测试在 beforeEach 之前读取尚未初始化的 tempDir
```

最后一项才是原始触发点；在 `git init` 附近增加默认目录只能掩盖症状。

## 添加诊断信息

无法从现有调用栈确定来源时，在危险操作之前记录上下文：

```typescript
console.error('DEBUG before git init', {
  directory,
  cwd: process.cwd(),
  nodeEnv: process.env.NODE_ENV,
  stack: new Error().stack,
});
```

在测试中优先使用确定会显示的输出通道。日志至少包含：

- 关键参数
- 当前工作目录
- 相关环境或配置
- 完整调用栈
- 必要时包含时间和请求标识

获取证据后移除不再需要的临时日志，或将确有长期价值的内容降级为正式诊断日志。

## 定位状态污染测试

如果某个文件或目录只在完整测试集运行时出现，可使用
[`../examples/find-polluter.sh`](../examples/find-polluter.sh) 逐个运行测试并定位首个污染源。

该脚本假设项目使用 `npm test`，并采用线性扫描。执行前先检查并按当前项目的测试命令和文件匹配方式调整。

## 完成标准

只有同时回答以下问题，才算完成根因追踪：

- 错误值或状态最初在哪里产生？
- 为什么会产生？
- 它如何传播到失败位置？
- 哪项证据证明这条链路？
- 修复源头后，是否仍需要在高风险边界增加校验？
