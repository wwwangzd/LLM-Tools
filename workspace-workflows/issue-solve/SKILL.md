# 问题与实现需求的评估和处理

围绕用户提出的问题、改进或实现需求，整理目标与现状差距，评估成本和决策依赖，按用户规则实施并汇总结果。下文将需要处理的问题或需求统一称为“事项”。

在进入实现前判断事项是否适合当前范围处理。能够以合理成本可靠完成的事项直接推进；成本过高、依赖缺失或需要用户决策的事项保留并说明原因。

## 1. 确认目标与适用规则

综合当前对话、用户提供的清单、文档、表格、截图或链接，以及相关代码和文档，明确：

1. 需要解决的现象、补齐的缺口或实现的能力；
2. 涉及的模块、页面、功能或仓库范围；
3. 期望结果和可观察的验收条件；
4. 用户已经明确的约束、授权及适用的工作区或项目规范。

现有证据能够支持明确、低风险的理解时继续推进，并在必要时说明关键假设。若不同理解会导致不同的处理对象、产品体验、验收标准、权限边界或工作量，再向用户集中确认。

若来源需要权限、连接器或内部服务，先按工作区规则尝试访问，读取与当前事项有关的状态、描述、截图和附件。无法访问且现有上下文不足时，说明具体限制，请用户补充信息或权限，不得臆造内容。

## 2. 整理事项并核实当前状态

结合已知范围筛选仍需处理的记录，并用状态、验收备注、最近更新和代码现状去重。状态或预期含义存在歧义但不影响当前可安全推进的部分时，可以先继续检查；只有影响处理结论时才向用户确认。

多项事项保留来源编号或内部编号，每项记录：

1. 来源编号或可追溯标识；
2. 问题或需求描述和期望效果；
3. 涉及模块、功能、页面或组件；
4. 可用证据及截图、附件的可见情况；
5. 当前状态和判断依据。

单一简单事项无需为了格式建立冗长清单。

不要仅凭描述或列表文字直接修改。问题修复先在当前代码或运行行为中确认问题仍然存在；改进和实现需求先核对已有能力与目标之间的差距。

## 3. 成本与决策分流

在编码前逐项分类：

### 可直接处理

事项边界和验收标准足够清楚，改动局限，依赖可用，预计能以小范围修改及相称验证完成。直接实施。

### 成本过高，暂不处理

出现以下任一情况时先保留，不进入实现：

- 需要跨多个仓库或改动公共契约、架构、数据模型；
- 需要大面积重写、迁移或引入新基础设施；
- 所需依赖、权限、设计资产或环境缺失，无法可靠完成；
- 工作量明显超出当前事项批次或单个可审查变更；
- 风险与收益不匹配，低侵入方案不能满足需求。

记录具体成本来源和建议后续路径，不用模糊的“太复杂”代替分析。

### 需要用户决策

以下情况暂停该事项并向用户确认，获得选择后再继续：

- 存在两个以上会产生不同产品体验或技术边界的合理方案；
- 问题或需求描述、设计稿与现有行为冲突；
- 是否抽取公共能力、改变交互语义或扩大范围会显著影响结果；
- 缺少关键验收标准，合理假设可能偏离用户意图。

将同一批次的决策问题尽量合并询问。给出推荐项、各方案影响和必要证据；等待用户选择时，可以继续处理其他不依赖该决策的事项。

## 4. 实现中的复用、对齐与清理

只检查与当前事项和触达模块直接相关的内容。

### 4.1 优先复用已有能力

搜索现有公共函数、服务、组件库、设计 token、通用交互组件及同类实现。已有能力满足需求时直接复用，避免重复实现相同逻辑；涉及界面时，优先使用项目指定组件库及已有按钮、提示、加载态、弹窗、空态等通用能力。

不要为迁就局部实现而复制通用组件，也不要为了形式统一强行替换行为不同的组件。

### 4.2 对齐相似设计与实现

检查同一产品中是否已有相同或高度相似的业务逻辑、状态处理、界面、设计、交互或响应式规则：

1. 能直接复用且语义一致时复用。
2. 多处存在稳定、真实的重复需求，抽取后能降低重复且不会引入复杂 API 时，才考虑提取通用能力。
3. 没有必要提取时，不新增抽象；实现方式与既有同类能力对齐。涉及界面时，还要对齐视觉、状态文案、操作反馈、键盘、无障碍和响应式行为。

抽取公共能力会显著扩大改动范围时，归入“需要用户决策”或“成本过高”。

### 4.3 清理过时和无用内容

1. 识别被本次修改取代的代码、样式、逻辑、内容和注释。
2. 用引用搜索、动态类名检查、条件分支和运行行为确认既有内容是否仍被使用。
3. 删除已经证明无用且与当前事项直接相关的内容。
4. 移除本次修改产生的未使用导入、死代码和测试残留。

不要删除由模板字符串、状态映射、运行时选择器或平台差异动态使用的内容，也不要顺手清理无关存量问题。

## 5. 实施与核对结果

1. 改动前检查目标仓库状态，保留用户已有修改。
2. 按已明确的目标和适用规则完成最小范围实现；问题修复针对根因，不主动扩大功能。
3. 根据验收条件、改动风险和项目要求选择必要的测试或检查，复用当前修改后仍有效的证据。
4. 涉及界面且具备可运行环境时执行视觉或交互核对；无法视觉验证时明确标注。
5. 处理过程中发现成本、风险或影响范围显著扩大时，重新评估该事项，不勉强完成。
6. 除非用户明确要求，不提交、不推送、不发起 PR/MR，也不更新外部问题状态。

## 6. 汇总处理结论

最终回复必须包含以下两部分，并保留来源编号。验证结果统一放在对应事项中，说明关键依据、未验证项和残余风险，不重复展开相同证据。

### 已完成

按序号列出：

1. 问题或需求与原始编号；
2. 成本判断和实际处理范围；
3. 问题根因或原有能力缺口；
4. 实际修改；
5. 通用能力复用、设计对齐或清理结果；
6. 验证状态及支持该状态的关键依据。

### 未完成

按序号列出：

1. 问题或需求与原始编号；
2. 分类：成本过高、待用户决策、来源不足、无法复现、依赖缺失、验证不足或其他；
3. 未完成的具体原因，以及已经实施的部分；
4. 推荐的下一步或所需决策。

没有未完成事项时明确写“无”。缺少足够验证依据的事项不得列入“已完成”，也不把未验证内容表述为已完成。
