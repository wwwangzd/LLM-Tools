# 问题评估与处理

在进入实现前判断问题是否适合当前范围处理。能够以合理成本可靠解决的项目直接推进；成本过高、依赖缺失或需要用户决策的项目保留并说明原因。

## 1. 确定当前问题

综合当前对话、用户提供的清单、文档、表格、截图或链接，以及工作区中的代码和文档，判断：

- 需要解决的现象、缺口或问题项；
- 可能涉及的模块、页面、功能或仓库范围；
- 期望结果和可观察的验收条件；
- 用户已经明确的约束与授权。

现有证据能够支持明确、低风险的理解时继续推进，并在必要时说明关键假设。若不同理解会导致不同的处理对象、产品体验、验收标准、权限边界或工作量，再向用户集中确认。

若问题来源需要权限、连接器或内部服务，先按工作区规则尝试访问，并尽量读取状态、描述、截图和附件。无法访问且现有上下文不足时，说明具体限制，请用户粘贴内容、导出文件或补充权限，不得臆造问题。

## 2. 整理并确认候选问题

结合已知范围筛选仍需处理的记录，并用状态、验收备注、最近更新和代码现状去重。状态或预期含义存在歧义但不影响当前可安全推进的部分时，可以先继续检查；只有影响处理结论时才向用户确认。

按任务规模决定整理方式。多项问题保留来源编号或内部编号，并记录问题描述、期望效果、相关模块和当前判断；单一简单问题无需为了格式建立冗长清单。

不要仅凭列表文字直接修改。先在当前代码或运行行为中确认问题仍然存在；原因不明、复现不稳定或影响边界不清时，使用 `systematic-debugging` 定位根因后再判断修复成本。

## 3. 成本与决策分流

在编码前逐项分类：

### 可直接处理

问题边界和验收标准足够清楚，改动局限，依赖可用，预计能以小范围修改及相称验证完成。直接实施。

### 成本过高，暂不处理

出现以下任一情况时先保留，不进入实现：

- 需要跨多个仓库或改动公共契约、架构、数据模型；
- 需要大面积重写、迁移或引入新基础设施；
- 所需依赖、权限、设计资产或环境缺失，无法可靠完成；
- 工作量明显超出当前问题批次或单个可审查变更；
- 风险与收益不匹配，低侵入方案不能满足需求。

记录具体成本来源和建议后续路径，不用模糊的“太复杂”代替分析。

### 需要用户决策

以下情况暂停该问题并向用户确认，获得选择后再继续：

- 存在两个以上会产生不同产品体验或技术边界的合理方案；
- 问题描述、设计稿与现有行为冲突；
- 是否抽取公共能力、改变交互语义或扩大范围会显著影响结果；
- 缺少关键验收标准，合理假设可能偏离用户意图。

将同一批次的决策问题尽量合并询问。给出推荐项、各方案影响和必要证据；等待用户选择时，可以继续处理其他不依赖该决策的问题。

## 4. 检查复用、对齐与清理机会

只检查与当前问题和触达模块直接相关的内容。

### 4.1 优先复用已有能力

搜索现有公共函数、服务、组件库、设计 token、通用交互组件及同类实现。已有能力满足需求时直接复用，避免重复实现相同逻辑；问题涉及界面时，优先使用项目指定组件库及已有按钮、提示、加载态、弹窗、空态等通用能力。

不要为迁就局部实现而复制通用组件，也不要为了形式统一强行替换行为不同的组件。

### 4.2 对齐相似设计与实现

检查同一产品中是否已有相同或高度相似的业务逻辑、状态处理、界面、设计、交互或响应式规则：

1. 能直接复用且语义一致时复用。
2. 多处存在稳定、真实的重复需求，抽取后能降低重复且不会引入复杂 API 时，才考虑提取通用能力。
3. 没有必要提取时，不新增抽象；实现方式与既有同类能力对齐。问题涉及界面时，还要对齐视觉、状态文案、操作反馈、键盘、无障碍和响应式行为。

抽取公共能力会显著扩大改动范围时，归入“需要用户决策”或“成本过高”。

### 4.3 清理过时和无用内容

清理被本次修改取代的代码、样式、逻辑、内容和注释，以及本次产生的未使用导入、死代码和测试残留。

删除既有内容前，用引用搜索、动态类名检查、条件分支和运行行为证明其无用。不要删除由模板字符串、状态映射、运行时选择器或平台差异动态使用的内容，也不要顺手清理无关存量问题。

## 5. 实施与验证

- 改动前检查目标仓库状态，保留用户已有修改。
- 先修根因，再做最小范围实现，不主动扩大功能。
- 涉及功能或可观察行为修改且具备测试条件时，使用 `test-driven-development` 约束实现；不适合完整 TDD 时，选择与风险相称的替代验证并说明原因。
- 问题涉及界面且具备可运行环境时执行视觉或交互核对；无法视觉验证时明确标注。
- 处理过程中发现成本、风险或影响范围显著扩大时，重新评估该问题，不勉强完成。
- 准备结束任务或声称修复完成时，使用 `verification-before-completion` 获取最后一次相关修改之后的验证证据。
- 除非用户明确要求，不提交、不推送、不发起 PR/MR，也不更新外部问题状态。

## 6. 汇总结论

输出深度与问题数量相称。多项问题按“已处理”和“未处理”分组并保留编号；单一简单问题可以直接给出结论。

已处理项说明问题、成本判断、根因（适用时）、实际修改以及验证证据。

未处理项说明分类、具体原因和推荐下一步。分类可以包括成本过高、待用户决策、来源不足、无法复现、依赖缺失或其他。

最后简述未验证项和残余风险。没有未处理或未验证内容时明确写“无”，不把缺少证据的结果表述为已完成。
