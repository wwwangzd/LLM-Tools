# 记录需求来源并准备 Worktree

按“确认输入 → 获取来源信息 → 写入文档 → 创建 worktree → 验证”的顺序执行。此阶段只登记需求基础来源，不进入需求交互、澄清或研发分析。

## 1. 确认输入与工作区

1. 确认需求来源。来源可以是链接、任务或记录 ID、本地文件、粘贴内容，或用户给出的名称与 PRD 链接；未提供时先询问，不写文件、不 fetch、不创建 worktree。
2. 读取工作区级 `AGENTS.md`、`CONTEXT.md` 和文档约定，只用于识别工作区根目录、仓库清单和保存位置。
3. 确认目标仓库。只采用用户明确指定的仓库，或来源元数据中明确标注的仓库归属；无法确定时直接询问，不读取 PRD 正文、不搜索代码来推断。

## 2. 获取来源基础信息

若需求来源需要权限、连接器或内部服务，先按工作区规则尝试访问，并只读取本节所需的基础字段。无法访问且现有上下文不足时，说明具体限制，请用户提供链接、导出文件或补充权限，不得臆造来源信息。

只补齐以下字段：

- 需求名称；
- 来源类型或平台；
- 原始来源链接或标识；
- 来源定位，例如文档、空间、表、视图或记录 ID；
- PRD 规范链接；来源本身就是 PRD 时直接使用该链接。

字段齐全后立即停止读取。不要获取或记录 PRD 正文、背景、目标、范围、流程、验收标准、负责人、排期、依赖、风险、设计方案、代码入口或仓库影响分析。工具返回了额外内容时忽略，不写入文档。

无法确定需求名称或 PRD 链接时向用户补齐；需求明确没有 PRD 时，取得用户确认后记录“无”。不得臆造信息。

## 3. 写入来源文档

在 Git fetch 或 worktree 操作前写入：

```text
<workspace>/docs/requirements/<requirement-slug>.md
```

使用简短稳定的 kebab-case slug；有需求 ID 时优先包含。文件已存在时不得覆盖，先询问更新原文件还是使用新文件名。仅当工作区规范明确要求时更新文档索引。

文档只使用以下结构，`来源定位` 无可用信息时省略：

```markdown
# <需求名称>

- 来源类型：<平台或载体>
- 原始来源：<链接或标识>
- 来源定位：<文档、表、视图、记录 ID 等>
- PRD：<规范链接或经确认的“无”>
- 获取时间：<带时区的时间>
```

不得增加需求分析章节。写入后重新读取，确认名称、原始来源和 PRD 可追溯。

## 4. 准备目标仓库

1. 对用户指定的每个仓库运行 `git status --short` 和 `git worktree list`，保留已有修改，不提交、不 stash、不切换现有检出。
2. 多仓库需求为每个已明确指定的仓库创建 worktree；不要自行扩大仓库范围。
3. 分支名优先遵循用户给出的名称或仓库已有约定；没有明确约定时使用 `feat/<requirement-slug>`。
4. 多仓库工作区默认路径为 `<workspace>/.worktrees/<requirement-slug>/<repo-name>`。单仓库工作区使用 `<workspace-parent>/.worktrees/<requirement-slug>/<repo-name>`，避免嵌套到源仓库。

## 5. 从最新默认分支创建 Worktree

对每个目标仓库运行本 Skill 附带的脚本：

```bash
scripts/create_worktree.sh \
  --repo <repo-path> \
  --path <worktree-path> \
  --branch <branch-name>
```

远端不是 `origin` 时增加 `--remote <remote-name>`。脚本会 fetch 远端、探测默认分支并从最新远端引用创建新分支和 worktree；已有目标目录、本地分支或远端分支不会被复用或覆盖。

某个仓库创建失败时保留已成功结果，不做破坏性回滚；报告失败原因并等待用户决定。

## 6. 验证并交付

确认：

- 来源文档只包含基础来源字段，名称、来源和 PRD 可追溯；
- 每个 worktree 的分支正确，起始提交等于创建时远端默认分支提交；
- 原检出中的未提交修改仍然存在；
- 未执行 commit、push、stash、PRD 分析、代码检索或外部需求状态更新。

最终只报告文档路径、需求名称与 PRD、各仓库的默认分支/新分支/worktree 路径、验证结果和阻塞项。
